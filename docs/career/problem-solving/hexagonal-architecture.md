# 외부 변화로부터 비즈니스 로직 보호하기

## 1. 문제 (Problem)

### 통제 불가능한 외부의 변화가 핵심 로직을 오염

"돈 버는 서베이"는 금융권 공통 인프라인 **메타 모델**의 영향으로 DB 스키마가 강제로 변경되는 일이 빈번했습니다.

- **문제점**: DB 컬럼명이 바뀌거나 테이블 구조가 변경될 때마다, 비즈니스 로직(Service Layer)까지 수정해야 하는 전파 문제가 발생했습니다.
- **결과**: 단순한 명칭 변경에도 사이드 이펙트를 검토해야 했고, 정작 중요한 기획 요건 개발보다 인프라 대응에 더 많은 시간을 쏟게 되었습니다.

## 2. 선택 (Choice)

### 헥사고날 아키텍처(Hexagonal Architecture) 도입

외부 스키마의 변화가 도메인 중심부로 들어오지 못하도록 헥사고날 아키텍처를 선택했습니다.

- **도메인 모델 유지**: DB가 어떤 컬럼명을 쓰든 UseCase는 기획 의도에 맞는 순수한 도메인 언어만 사용하도록 설계.
- **어댑터 책임 분리**: DB의 물리적 스키마와 도메인 모델 사이의 매핑을 어댑터가 전담하게 하여, 외부의 변화를 어댑터 계층에서 차단.

## 3. 결과 (Result)

- **변경 격리 성공**: 실제로 전사 메타 모델 변경으로 테이블 컬럼명이 바뀌는 요구사항이 생겨도, **비즈니스 로직은 한 줄도 수정하지 않고 어댑터 매핑만 수정**하여 즉시 대응했습니다.
- **유지보수 효율**: 기획 변경 시에는 UseCase만, 스키마/인터페이스 변경 시에는 Adapter만 수정하면 되는 구조가 확보되어 개발 생산성이 향상되었습니다.
