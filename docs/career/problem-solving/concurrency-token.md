# 대규모 선착순 트래픽의 경합 분산 전략

## 1. 문제 (Problem)

### 퀴즈 정답 제출 트래픽의 급증

매일 특정 시간에 퀴즈가 오픈되면 **오픈 직후 수천 명의 트래픽이 동시에 몰리는 특성**이 있을거라 예상했습니다.
특히 '문제 조회'보다 **'정답 제출(Submit Answer)'** API의 트래픽 비중이 압도적으로 높습니다. 사용자는 정답을 맞출 때까지 반복적으로 오답을 제출하기 때문입니다.

### 선착순 처리의 병목

선착순 혜택을 제공하기 위해서는 반드시 **남은 수량**이라는 공유 자원에 대한 동기화가 필요합니다.

- **Critical Section**: 동시에 들어온 요청들이 선착순 수량을 점유하려고 경쟁합니다.
- **Risk**: DB Row Lock 경합이 심해지면 Connection Pool이 고갈되고, 이는 전체 서비스 장애로 이어질 수 있습니다.

## 2. 전략 (Strategy)

선착순 경합 자체를 완전히 제거할 수는 없으므로, **경합이 발생하는 임계 영역을 명확히 정의하고, 그 범위를 최소화**하는 것을 목표로 리워드 타입별 이원화된 전략을 수립했습니다.

### A. 쿠폰: 미리 발급된 토큰의 경합 분산

제휴사 쿠폰처럼 미리 발급이 가능한 경우, **물리적인 Row Lock을 여러 개로 쪼개어 경합을 분산**시키는 전략을 사용했습니다.

- **Token Pre-issue**: 선착순 수량만큼(예: 1,000개)의 유니크 토큰(Row)을 미리 `INSERT`.
- **SKIP LOCKED**: 사용자가 요청 시, **비어있는 토큰을 하나 가져오되, 락이 걸린 행은 건너뛰고 다음 행을 점유**.
  ```sql
  SELECT * FROM coupon
  WHERE use_yn = 'N'
  LIMIT 1
  FOR UPDATE SKIP LOCKED;
  ```
- **Effect**: 모든 트랜잭션이 **서로 다른 Row**를 점유하므로, DB Lock 대기 시간이 획기적으로 감소합니다.

### B. 현금: 카운트 제어와 경합 빈도 조절

현금성 포인트처럼 미리 실체를 만들 수 없는 경우, **단일 Count Row**를 제어하되 **유입 속도를 구조적으로 조절**하여 경합을 완화했습니다.

- **구조적 경합 완화**: 캐시백은 'Hard' 난이도 정답자만 시도 가능하게 하여, DB에 도달하는 트래픽의 물리적 총량을 **구조적으로 낮춤**.
- **Atomic Update**: `Check-Then-Act` 형태가 아닌, 원자적인 처리로 동시성 문제를 해결.

  ```sql
  UPDATE problem_reward_quota
  SET quota = quota - 1
  WHERE id = :problemId
    AND quota > 0;
  ```

## 3. 검증 및 성과 (Outcome & Verification)

- **정합성 보장**: 동시성 테스트를 통해 수천 건의 동시 요청 상황에서도 중복 지급이나 초과 지급 없이 선착순 비즈니스 로직이 정확히 수행됨을 확인했습니다.
- **운영 안정성 설계**: 리워드 타입별 경합 분산 전략을 통해, 특정 리워드의 트래픽 쏠림이 전체 시스템의 데이터베이스 커넥션 고갈로 번지지 않도록 리스크를 분산했습니다.
