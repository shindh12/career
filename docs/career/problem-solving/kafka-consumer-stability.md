# Kafka Consumer 안정성 확보 및 마이그레이션 구조 개선

## 1. 문제 (Problem)

### 1.1. 상황 및 잔존 리스크

운영 중인 RDB 데이터를 Redis 비트맵으로 전환하기 위한 대규모 마이그레이션 과정에서 발생한 문제입니다. Cutover를 통해 실시간 적재 체계는 이미 확보된 상태였으며, **Kafka 이벤트를 활용해 1회성으로 과거 데이터를 Backfill** 하던 중 기술적 병목에 직면했습니다.

특히 특정 `tagId`에 데이터가 비정상적으로 쏠려 있는 **Data Skew** 케이스에서 DB 조회 속도가 급격히 저하되었으며, 인덱스 쿼리 튜닝 대응 후에도 다음과 같은 리스크가 구조적으로 남아있었습니다.

- **Hot Key (Worst Case)의 존재**: 특정 태그(최대 120만 건)가 할당된 파티션만 처리가 길어지며 `max.poll.interval.ms`(5분)를 초과할 위험이 상존했습니다.
- **Consumer 가용성 붕괴**: 처리 시간이 임계치를 넘기면 Rebalancing이 발생하고, 작업 중인 offset이 commit되지 않아 동일 이벤트가 무한 재처리되는 루프에 빠졌습니다.

### 1.2. 문제의 본질

> **"DB 실행 계획이 흔들릴 수 있는 상황에서, Kafka Consumer가 단일 이벤트를 너무 오래 점유하여 전체 그룹의 안정성을 해치는 구조"**

쿼리 튜닝만으로는 Worst Case를 완벽히 제거할 수 없으므로, **쿼리가 느려져도 시스템이 무너지지 않는 구조적 개선**이 필요했습니다.

---

## 2. 전략 (Strategy)

### 2.1. DB 조회 시간 안정화 (원인 감소)

- **Read-only Routing**: 트랜잭션에 `readOnly`를 적용하여 Replica DB로 조회를 분산, Master DB 부하를 차단했습니다.
- **Optimizer Hint**: `FORCE INDEX` 등을 통해 `tag_id` 인덱스를 명시적으로 타도록 유도하여 실행 계획의 흔들림을 최소화했습니다.

### 2.2. Worst Case 대응: Chunking 과 Interval 상한 설정

단순히 Kafka의 타임아웃 설정을 늘리는 것은 한계가 있으므로, 작업 자체를 유동적으로 분할하는 전략을 취했습니다.

- **Poll Interval 조정**: 특정 토픽에 대해 `max.poll.interval.ms`를 10분으로 증가시켰습니다.
- **Self-Chaining Chunking**: 이벤트 처리 중 소요 시간을 실시간 트래킹합니다. 만약 처리 시간이 설정된 임계치(예: 8분)에 근접할 경우, **현재까지 처리된 ID를 기준으로 새로운 이벤트를 발행**하고 현재 메시지는 즉시 commit 후 종료합니다.
- **효과**: Rebalancing을 구조적으로 차단하며, 실패 시에도 처음부터가 아닌 마지막 처리 지점부터 이어서 작업이 가능해졌습니다.

### 2.3. 처리량 극대화 및 파티션 단위 영향 격리

- **파티션 단위 독립 처리**: Kafka 메시지 `key`를 `tagId`로 지정하여 동일 태그의 데이터가 특정 파티션에 고정되도록 했습니다. 이를 통해 특정 Hot Key 파티션이 DB 지연으로 느려지더라도, 다른 파티션을 처리하는 스레드들은 영향을 받지 않고 작업을 지속할 수 있게 했습니다.
- **Concurrency 최적화**: 파티션 수(12개)와 인스턴스(3대)에 맞춰 리스너 `concurrency`를 4로 상향하여 전체 마이그레이션 처리량을 높였습니다.
- **리밸런싱 방어**: 리벨런싱은 컨슈머 그룹 전체의 작업을 일시 중단시키는 Stop-the-world 이벤트이므로, 이를 방지하는 것이 안정성의 핵심입니다. 앞서 언급한 **Self-Chaining Chunking**을 통해 모든 처리가 정해진 `poll interval` 내에 완료되도록 강제함으로써 리밸런싱 없는 안정적인 마이그레이션 환경을 구축했습니다.

### 2.4. 리스크 격리 및 수동 선처리

- **모니터링**: 단계별 처리 시간 로깅과 에러 발생 시 즉시 알림 체계를 구축하여 지연 지점을 즉각 식별할 수 있게 했습니다.
- **수동 선처리**: 데이터 스큐가 심한 것으로 파악된 과거 장애 이력 태그(Hot Key)들은 전체 자동 마이그레이션 프로세스에 영향을 주지 않도록 운영자의 통제 하에 사전에 따로 수동 처리를 진행하여 리스크를 원천 격리했습니다.

---

## 3. 결과 (Result)

### 3.1. 시스템 안정성 확보

- **Rebalancing 무한 반복 제거**: 단일 이벤트가 컨슈머를 점유하는 시간을 구조적으로 상한 제어함으로써 안정적인 Lag 감소를 달성했습니다.
- **장애 내성 강화**: "느린 쿼리 1건"이 전체 마이그레이션 실패로 이어지지 않는 견고한 구조를 확보했습니다.

### 3.2. 정합성 및 효율성

- **멱등성 보장**: 작업 쪼개기와 멱등(Idempotent) 처리 기반으로 중복 소비가 발생해도 결과의 정합성을 유지했습니다.
- **핵심 성과**: **"쿼리를 고친 게 아니라, 쿼리가 느려져도 시스템이 무너지지 않게 구조를 바꿨다."**
