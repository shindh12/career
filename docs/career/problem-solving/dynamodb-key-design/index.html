액세스 패턴 최적화를 통한 대량 마이데이터 DynamoDB 설계

1. 문제 (Problem)​

마이데이터 표준 스펙의 정형성과 NoSQL의 물리적 한계​

마이데이터 플랫폼 구축 당시, 수백 개의 정보제공자로부터 수집되는 수억 건의 데이터를 안정적으로 적재하고 서비스해야 했습니다.

  • 액세스 패턴: 다양한 업권(은행, 카드 등)의 거래 내역은 규격은 다르지만 '시간순 조회'라는 고정된 패턴을 가집니다. 이를 유연하게 수용하면서도 쓰기 성능과 수평적 확장을 보장하기 위해 DynamoDB를 선택했습니다.
  • 역할 분리: 플랫폼은 대량 수집 및 적재에 집중하고, 서비스는 지연 없는 조회에 집중하는 구조적 최적화가 필요했습니다.

2. 전략 (Strategy)​

1) 액세스 패턴 정의 (Access Patterns)​

설계에 앞서 사용자의 대표적인 조회 요구사항을 두 가지로 도출했습니다.

  • AP1: 사용자의 전체 거래내역 조회 (통합 타임라인)
  • AP2: 사용자의 개별 자산(계좌, 카드 등)별 상세 거래내역 조회

2) 단일 테이블 설계 (Base Table & GSI)​

두 조회 패턴을 각기 다른 테이블에 저장할지 고민했으나, 트랜잭션 관리의 단순화와 데이터 정합성을 인프라(DynamoDB) 수준에서 보장받기 위해 'Base Table + GSI' 구조를 선택했습니다.

Base Table (AP1 대응)​

  • PK: USER#{userId}
  • SK: T#<transDtime>#{transNo}
  • TTL: expireAt = transDtime + 5 years (5년치 데이터 유지)
  • 의도: 사용자별 통합 타임라인을 시간 역순으로 즉시 조회 가능하도록 물리적 정렬을 구성했습니다.

자산별 GSI (AP2 대응)​

  • GSI1_PK: ASSET#{userId}#{industry}#{provider}#{assetId}
  • GSI1_SK: T#{transDtime}#{transNo}
  • 의도: 특정 자산 별 거래내역 조회 액세스 패턴은 GSI를 통해 재구성하였습니다.

3. 결과 (Result)​

  • 액세스 패턴 중심의 모델링 역량 확보: "데이터 수집"보다 "데이터 조회" 요구사항을 최우선으로 두고 PK/SK 구조를 설계하는 과정을 통해, NoSQL의 물리적 구조를 비즈니스 요구사항에 최적화하는 모델링 기법을 체득했습니다.
  • 인프라를 활용한 정합성 보장 구조 마련: 애플리케이션 레이어의 복잡한 정합성 로직을 줄이기 위해 DynamoDB의 인프라 기능(Base Table-GSI 동기화)을 적극 활용함으로써, 시스템의 단순성을 유지하면서도 데이터 무결성을 높이는 실무적인 관점을 정립했습니다.
  • 대용량 데이터 환경의 아키텍처적 타당성 검증: 수억 건의 데이터 규모에서도 일정한 성능(Latency)을 유지할 수 있는 NoSQL 기반 아키텍처 설계가 대형 금융 플랫폼 환경에서 기술적으로 유효함을 확인했습니다.
