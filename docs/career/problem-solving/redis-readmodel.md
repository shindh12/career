# 서베이 도메인 복잡도 해소: CQRS와 Redis ReadModel

## 1. 문제 (Problem)

### 계층적 도메인 구조와 Join 부하

"돈 버는 서베이" 서비스의 도메인은 **설문지 > 질문지 > 응답지**로 이어지는 계층 구조로 이루어져 있습니다.

- **복잡도 증가**: 사용자에게 설문 목록을 노출할 때마다 이 계층 구조를 전체 Join하여 조회하는 것은 쿼리 복잡도를 높이고 성능 저하를 유발했습니다.
- **성능상의 한계**: 타게팅 조건(성향/자산 등)과 결합될 경우, 매번 RDB에서 구조화된 데이터를 만들어내는 비용이 불필요하게 반복되었습니다.

## 2. 전략 (Strategy)

### CQRS 아키텍처 도입

데이터의 변경(Command)과 조회(Query) 책임을 명확히 분리하여, 서비스 조회 시점에는 이미 완성된 형태의 'Read Model'만 읽도록 설계했습니다.

1.  **Command (Admin)**: 어드민에서 설문 생성/수정 시 RDB에 정규화된 상태로 데이터를 저장합니다.
2.  **Query Model 생성**: 데이터 변경 시점 혹은 주기적 동기화 프로세스를 통해 서비스에서 바로 사용할 수 있는 형태의 **구조화된 리드 모델**을 생성합니다.
3.  **Redis 전파**: 생성된 리드 모델을 Redis에 캐싱하여 서비스 서버가 RDB Join 없이 데이터를 즉시 대입할 수 있게 합니다.

### 데이터 조회 흐름 (Data Flow)

1.  **Step 1**: 사용자의 성향/속성/태그 정보를 기반으로, 노출 대상인 **설문 ID 목록**만 빠르게 추출합니다.
2.  **Step 2**: 추출된 각 ID를 Key로 하여 Redis에서 미리 생성된 **Read Model**을 일괄 조회하여 사용자에게 전달합니다.

## 3. 결과 (Result)

- **성능 최적화**: 복잡한 서비스 로직 내에서 RDB Join이 사라지며 목록 조회 성능이 비약적으로 향상되었습니다. (평균 응답 시간 50ms 미만 유지)
- **복잡도 격리**: 서비스 서버는 도메인의 정규화 구조를 몰라도 Read Model만으로 화면을 구성할 수 있게 되어 코드가 단순해졌습니다.
- **확장성**: 설문 구조가 더 복잡해지더라도 Read Model 생성 단계에서만 반영하면 되므로, 서비스 조회 성능에는 영향을 주지 않는 구조를 확보했습니다.
