# 구간별 관측 가능성(Observability) 확보

## 1. 문제 (Problem)

### 단일 API 내 복잡한 비즈니스 로직의 혼재

AI 키워드 퀴즈 서비스의 **정답 제출 API**는 트래픽이 집중되면서도 아래와 같이 여러 외부 의존성과 로직이 혼재된 복잡한 구조였습니다.

1.  **정답일 경우**: 선착순 정책 확인(DB Lock/Redis) → 리워드 지급(Offer 모듈 호출/지급내역 저장)
2.  **오답일 경우**: 가드레일 검증 → 임베딩 벡터 조회(외부 모델 API) → 유사도 계산
3.  **공통**: 정답/오답 이력 저장(DB Write)

**이슈**: API latency가 튈 때, **"임베딩 서버가 느린건지", "DB 선착순 경합 때문인지", "단순 리워드 지급 지연인지"** 원인을 즉각 파악하기 어려울거라 생각했습니다.

## 2. 전략 (Strategy)

### A. 구간 별 메트릭 수집

단일 API 내부를 **논리적인 구간**으로 나누고, 각 구간을 담당하는 메서드에 `@Observed`를 적용하여 독립적인 메트릭을 수집했습니다. 이를 통해 전체 응답 시간을 계층적으로 분석할 수 있는 기반을 마련했습니다.

- **정답 Path**: `선착순 판별` + `리워드 지급` + `정답 이력 저장`
- **오답 Path**: `가드레일 검증` + `임베딩 벡터 조회` + `유사도 계산` + `오답 이력 저장`

### B. 구간 별 대시보드 구축

수집된 구간별 Latency 메트릭을 바탕으로, 장애나 병목 발생 시 원인을 즉시 식별할 수 있는 대시보드를 구축했습니다.

- **정답 입력 API Latency = 오답 Latency + 정답 Latency**
  - 어떤 경로(Path)에서 지연이 발생하는지 1차로 식별합니다.
- **정답 Latency = 선착순 판별 Latency + 리워드 지급 Latency + 정답 저장 Latency**
  - 정답 처리 구간 내에서 선착순 로직의 병목 여부 등을 예측합니다.
- **오답 Latency = 가드레일 Latency + 임베딩 벡터 API 호출 Latency + 유사도 계산 Latency + 오답 저장 Latency**
  - 오답 처리 구간 내에서 외부 임베딩 연계 지연 여부를 예측합니다.

## 3. 결과 (Result)

- **장애 인지**: "전체 에러"가 아닌 "임베딩 검색 지연"임을 대시보드에서 1분 내 파악 가능해짐.
- **비즈니스 인사이트**: 정답률, 오답 패턴 등을 실시간으로 분석하여 퀴즈 난이도 조절에 활용도 가능.
